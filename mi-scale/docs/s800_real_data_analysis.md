# Анализ реальных BLE-данных Xiaomi Mijia S800

## Дата исследования
2025-11-18

## Информация об устройстве
- **Модель**: MJTZC04YM (Xiaomi Mijia Body Composition Scale S800)
- **MAC-адрес**: `D4:43:8A:CD:3F:76`
- **Локальное имя**: `Mijia Scale S800 3F76`
- **Протокол**: Mi Beacon (MiOT BLE)

---

## 1. Обзор обнаруженного протокола

### 1.1. Ключевые выводы
✅ **Устройство использует протокол Mi Beacon (UUID: `0000fe95-0000-1000-8000-00805f9b34fb`)**  
✅ **Данные передаются через `service_data` и `manufacturer_data`**  
✅ **Присутствуют как открытые, так и зашифрованные пакеты**  
⚠️ **Для полного доступа к данным измерений требуется ключ шифрования (bindkey)**

### 1.2. Типы обнаруженных пакетов

| Тип пакета | Длина | Frame Control | Описание |
|------------|-------|---------------|----------|
| Короткий (beacon) | 12 байт | `0x10` | Периодические маячковые пакеты без данных измерений |
| Короткий (изменённый) | 12 байт | `0x10` с изменённым 2-м байтом | Указывает на изменение состояния устройства |
| Длинный (открытый) | 20 байт | `0x58` | Пакет с данными, возможно частично открытыми |
| Длинный (зашифрованный) | 24 байт | `0x48` | Полностью зашифрованный пакет с измерениями |

## 2. Детальный анализ пакетов

### 2.1. Короткие маячковые пакеты (Beacon)

**Пример 1** (устройство в покое):
```
Service Data UUID: 0000fe95-0000-1000-8000-00805f9b34fb
Raw bytes: 10 59 e2 51 08 76 3f cd 8a 43 d4
Hex string: 1059e25108763fcd8a43d4
```

**Разбор структуры:**
```
Offset | Bytes      | Поле                | Значение        | Описание
-------+------------+---------------------+-----------------+---------------------------
0      | 10         | Frame Control       | 0x10            | Тип фрейма: незашифрованный beacon
1-2    | 59 e2      | Product ID          | 0xE259          | Идентификатор продукта (S800)
3-4    | 51 e2      | Frame Counter       | 0xE251          | Счётчик фреймов (инкрементируется)
5      | 08         | Packet Counter      | 0x08            | Счётчик пакетов
6-11   | 76 3f cd 8a 43 d4 | MAC Address  | D4:43:8A:CD:3F:76 | MAC в обратном порядке (LE)
```

**Пример 2** (устройство активировалось):
```
Raw bytes: 10 5b e2 51 08 76 3f cd 8a 43 d4
Изменение: байт 1 изменился с 0x59 на 0x5B
```

Байт 1 (второй байт фрейма) может содержать флаги состояния:
- `0x59` = устройство в режиме ожидания
- `0x5B` = устройство активировано (пользователь на весах)

### 2.2. Длинный открытый пакет (Measurement - частично открытый)

**Пакет во время измерения:**
```
Service Data UUID: 0000fe95-0000-1000-8000-00805f9b34fb
Raw bytes: 58 59 e2 51 09 76 3f cd 8a 43 d4 44 3d 88 57 00 00 00 03 32 5d 30
Hex string: 5859e25109763fcd8a43d4443d88570000000332 5d30
Length: 20 bytes
```

**Разбор структуры:**
```
Offset | Bytes      | Поле                | Значение        | Описание
-------+------------+---------------------+-----------------+---------------------------
0      | 58         | Frame Control       | 0x58            | Длинный фрейм с данными
       |            | bit 6: Encrypted    | 0               | Данные НЕ зашифрованы
       |            | bit 4: MAC included | 1               | MAC адрес включён
       |            | bit 3: Capability   | 1               | Поддержка возможностей
1-2    | 59 e2      | Product ID (part)   | 0xE259          | Продукт
3-4    | 51 e2      | (reversed)          |                 |
5      | 09         | Frame Counter       | 0x09            | Счётчик фреймов
6-11   | 76 3f cd 8a 43 d4 | MAC Address  | D4:43:8A:CD:3F:76 | MAC в обратном порядке

--- PAYLOAD (Object data) ---
12-13  | 44 3d      | Object ID           | 0x3D44          | Тип объекта (измерение)
14     | 88         | Object Length       | 0x88            | Длина данных объекта
15-19  | 57 00 00 00 03 | Data           | ?               | Данные измерения
20-22  | 32 5d 30   | ?                   | ?               | Возможно, дополнительные данные
```

**Анализ Object ID `0x3D44`:**
- В Mi Beacon протоколе используются стандартные Object ID для разных типов данных
- Возможные значения для весов: вес (weight), импеданс (impedance), стабилизация
- Требуется сопоставление с документацией Mi Beacon

**Данные измерения (байты 15-19):**
```
57 00 00 00 03
```
- `0x57` (87 decimal) - возможно, вес в специальной единице
- `0x00 0x00 0x00` - резерв или дополнительные флаги
- `0x03` - возможно, единица измерения (kg/lbs) или флаг стабилизации

### 2.3. Длинные зашифрованные пакеты (Encrypted Measurements)

**Пример 1:**
```
Service Data UUID: 0000fe95-0000-1000-8000-00805f9b34fb
Raw bytes: 48 59 e2 51 0a 9e c3 04 5d f1 8a ef de c8 83 fd a3 00 00 00 ba c0 76 7f
Hex string: 4859e2510a9ec3045df18aefde c883fda30000 00bac0767f
Length: 24 bytes
```

**Разбор структуры:**
```
Offset | Bytes      | Поле                | Значение        | Описание
-------+------------+---------------------+-----------------+---------------------------
0      | 48         | Frame Control       | 0x48            | Зашифрованный фрейм
       |            | bit 6: Encrypted    | 1               | Данные ЗАШИФРОВАНЫ
       |            | bit 3: Capability   | 1               | Поддержка возможностей
1-2    | 59 e2      | Product ID          | 0xE259          | Продукт S800
3-4    | 51 e2      |                     |                 |
5      | 0a         | Frame Counter       | 0x0A            | Счётчик (увеличился)
6-11   | 9e c3 04 5d f1 8a | Encrypted MAC? | (зашифровано)  | Возможно, часть MAC + nonce

--- ENCRYPTED PAYLOAD ---
12-23  | ef de c8 83 fd a3 00 00 00 ba c0 76 7f | Ciphertext | Зашифрованные данные
```

**Frame Counter инкрементация:**
```
Пакет 1: 0x0A
Пакет 2: 0x0B
Пакет 3: 0x0C
Пакет 4: 0x0D
Пакет 5: 0x0E
Пакет 6: 0x0F
```
Frame Counter используется для генерации nonce при шифровании AES-CCM.

### 2.4. Manufacturer Data

**Формат:**
```
Company ID: 911 (0x038F) - Xiaomi Inc.
Data: 10 59 e2 51 0a 76 3f cd 8a 43 d4
```

Структура аналогична короткому beacon пакету. Дублирует часть информации из service_data.

## 3. Протокол шифрования Mi Beacon

### 3.1. Алгоритм шифрования
- **Алгоритм**: AES-CCM (Counter with CBC-MAC)
- **Ключ**: 16 байт (128 бит) - bindkey устройства
- **Nonce**: 12 байт, формируется из MAC, Product ID, Frame Counter
- **Tag**: 4 байта (аутентификация)

### 3.2. Получение bindkey

**Метод 1: Через Mi Home (Android)**
1. Активировать режим разработчика в Mi Home
2. Добавить устройство в Mi Home
3. Извлечь токены через ADB или логи приложения
4. Использовать инструмент `python-miio` для извлечения bindkey

**Метод 2: Через облачный API Xiaomi**
1. Авторизоваться в Mi Cloud API
2. Получить список устройств и их токенов
3. Bindkey хранится в метаданных устройства

**Метод 3: Сниффинг начального pairing**
- При первом сопряжении устройства с Mi Home происходит обмен ключами
- Можно перехватить bindkey через BLE sniffing (требуется специальное оборудование)

### 3.3. Формат nonce (предположительный)

```
Nonce (12 байт) = MAC (6 байт) + Product ID (2 байта) + Frame Counter (4 байта)
Пример: d4 43 8a cd 3f 76 + e2 51 + 00 00 00 0a
```

### 3.4. Процесс расшифровки (псевдокод)

```python
from Crypto.Cipher import AES
import struct

def decrypt_mibeacon(ciphertext, bindkey, mac, product_id, frame_counter):
    # Формирование nonce
    nonce = mac + product_id + struct.pack('<I', frame_counter)
    
    # Создание cipher
    cipher = AES.new(bindkey, AES.MODE_CCM, nonce=nonce, mac_len=4)
    
    # Расшифровка
    plaintext = cipher.decrypt_and_verify(ciphertext[:-4], ciphertext[-4:])
    
    return plaintext

# Пример использования
bindkey = bytes.fromhex('XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX')  # 32 hex chars = 16 bytes
mac = bytes.fromhex('d4438acd3f76')
product_id = bytes.fromhex('e251')
frame_counter = 0x0a
ciphertext = bytes.fromhex('efde c883fda30000 00bac0767f')  # Примерные данные

plaintext = decrypt_mibeacon(ciphertext, bindkey, mac, product_id, frame_counter)
```

## 4. Интерпретация данных измерений

### 4.1. Возможные Object ID для весов

Основываясь на Mi Beacon спецификации и других устройствах Xiaomi:

| Object ID | Название         | Длина | Описание |
|-----------|------------------|-------|----------|
| `0x0607`  | Weight (no load) | 2-4   | Вес без нагрузки (калибровка) |
| `0x0607`  | Weight           | 2-4   | Текущий вес в граммах или единицах |
| `0x0A06`  | Impedance        | 2     | Биоимпеданс в Ом |
| `0x1006`  | Weight removed   | 1     | Флаг: вес удалён (стабилизация) |
| `0x3D44`  | Body metrics     | 8+    | Комплексные данные тела (вес + импеданс) |

**Примечание**: Точные Object ID для S800 требуют подтверждения через расшифровку реальных данных.

### 4.2. Формат данных веса (предположительный)

После расшифровки payload может выглядеть так:
```
Object ID: 0x0607 (Weight)
Length: 4 bytes
Data: 57 3d 00 00

Интерпретация:
- Вес (little-endian): 0x00003d57 = 15703 (в граммах?) → 15.703 кг
- Или: 0x3d57 = 15703 (в единицах 0.01 кг) → 157.03 кг
```

**Требуется проверка**: сопоставить расшифрованные значения с фактическим весом на дисплее весов.

### 4.3. Формат данных импеданса (предположительный)

```
Object ID: 0x0A06 (Impedance)
Length: 2 bytes
Data: f4 01

Интерпретация:
- Импеданс (little-endian): 0x01f4 = 500 Ом
```

## 5. Сценарии использования пакетов

### 5.1. Последовательность пакетов при измерении

1. **Idle state** (устройство в покое):
   - Короткие beacon пакеты: `10 59 e2 51 08 ...`
   - Частота: ~1-2 раза в секунду

2. **User step on** (пользователь встал на весы):
   - Изменение beacon: `10 5b e2 51 08 ...` (байт изменился)
   - Начало передачи измерений

3. **Weight stabilizing** (вес стабилизируется):
   - Зашифрованные пакеты: `48 59 e2 51 0a ...`, `0b`, `0c`, `0d`
   - Частота: ~3-5 пакетов в секунду
   - Frame Counter увеличивается

4. **Weight stabilized** (вес стабилизирован):
   - Открытый пакет (?): `58 59 e2 51 09 ...` с данными
   - Или финальный зашифрованный пакет с полными данными

5. **Measurement complete** (измерение завершено):
   - Возврат к beacon пакетам: `10 59 e2 51 0f ...`

### 5.2. Рекомендуемая логика обработки

```python
def process_s800_packet(advertising_data):
    service_data = advertising_data.service_data.get('0000fe95-0000-1000-8000-00805f9b34fb')
    
    if not service_data:
        return None
    
    frame_control = service_data[0]
    
    if frame_control == 0x10:
        # Короткий beacon - игнорируем или используем для отслеживания состояния
        return None
    
    elif frame_control == 0x58:
        # Длинный открытый пакет - попытка парсинга
        return parse_unencrypted_measurement(service_data)
    
    elif frame_control == 0x48:
        # Зашифрованный пакет - требуется bindkey
        if BINDKEY:
            return decrypt_and_parse_measurement(service_data, BINDKEY)
        else:
            logging.warning("Encrypted packet detected, but no bindkey configured")
            return None
    
    else:
        logging.debug(f"Unknown frame control: {hex(frame_control)}")
        return None
```

## 7. Требования к реализации

### 7.1. Базовая поддержка (без bindkey)

**Возможности:**
- ✅ Обнаружение устройства по MAC и локальному имени
- ✅ Определение начала измерения (изменение beacon)
- ⚠️ Частичный парсинг открытых пакетов (если доступны)
- ❌ Полный доступ к весу и импедансу (только с bindkey)

**Реализация:**
```python
def parse_s800_beacon(service_data):
    """Парсинг короткого beacon пакета."""
    if len(service_data) < 12:
        return None
    
    frame_control = service_data[0]
    state_flag = service_data[1]
    
    return {
        'active': state_flag == 0x5B,
        'idle': state_flag == 0x59
    }
```

### 7.2. Полная поддержка (с bindkey)

**Требования:**
- Параметр конфигурации `MISCALE_BINDKEY` (32 hex символа)
- Установка библиотеки `pycryptodome` для AES-CCM
- Логика расшифровки и парсинга

**Пример конфигурации:**
```json
{
  "MISCALE_MAC": "D4:43:8A:CD:3F:76",
  "MISCALE_MODEL": "s800",
  "MISCALE_BINDKEY": "0123456789abcdef0123456789abcdef"
}
```

### 7.3. Дополнения к requirements.txt

```
pycryptodome>=3.19.0  # Для AES-CCM расшифровки
```
